## 0. Критическая оценка (состояние на 2026-10-05)

Код в хорошем состоянии: `go build`, `go vet` и `gofmt` чистые, 1119 тестов зелёные.
Инварианты соблюдены, безопасность продумана глубже, чем у большинства аналогов.
Но продукт пока не доказывает, что он лучше, чем просто запустить `claude` в репозитории.
Ниже — что мешает, от главного к второстепенному.

### 0.1 Ценность ядра не доказана
- Нет ни одного измерения, что адаптивный выбор стадий даёт лучше результат или меньшую
  стоимость, чем `claude -p "<task>"`. Пороги `policy.*` не откалиброваны. Jev недоступен,
  `jev.mock` — эвристика по ключевым словам.
- До начала работы тратится до трёх LLM-вызовов: translate, context depth, classify.
  Каждый — холодный старт CLI. Окупаются ли эти накладные расходы, неизвестно.
- Сложность (`simple/medium/complex`) влияет только на `policy.stages.force`. Модель и
  effort жёстко заданы на действие. Главный рычаг экономии — дешёвая модель на простых
  задачах — не используется.

### 0.2 Implement работает вслепую — главный проигрыш в качестве
- У `implement` нет shell (`domain.AuthorityEdit` = Read, Grep, Glob, Edit, Write). Модель
  не может собрать проект или запустить тест. Цикл «правка → проверка» идёт через
  оркестратор: новая холодная сессия, максимум `max_fix_iterations: 2`. Голый Claude Code
  внутри одной сессии итерирует десятки раз. Безопасность куплена ценой качества, а это
  можно вернуть, не давая shell (задача Q2).
- Каждая стадия — отдельный вызов `claude --print`, между ними передаются только summary.
  `analysis.affected_files`, `analysis.risks`, `plan.affected_files` и `plan.risks` до
  `implement` не доходят (`internal/action/prompts.go`, `BuildImplementPrompt`). Review
  получает только summary анализа и плана. Каждая стадия заново читает репозиторий.
- Нет базового прогона тестов. Если тесты красные ещё до запуска, `implement` «чинит» чужие
  поломки, сжигает итерации, а run падает с непонятной причиной.
- При повторе `implement` видит только summary прошлой попытки, а не её diff. Нет
  остановки, когда прогресса нет (diff не изменился, та же ошибка теста).

### 0.3 Конкретные дефекты
- **Промпт передаётся одним аргументом argv** (`internal/provider/claude/client.go`, `args`:
  промпт последним элементом). В Linux одна строка argv ограничена `MAX_ARG_STRLEN`
  (128 КиБ). Diff и вывод тестов вставляются в промпт без ограничения размера
  (`fence(...)` в `prompts.go`, `Repository.Diff`). Большой diff (lock-файл,
  сгенерированный код) или длинный лог падающих тестов → `exec` падает с `E2BIG`. Ещё
  раньше раздувается контекст и стоимость.
- **Тестовая команда без sandbox получает почти всё окружение разработчика.**
  `ScrubbedEnv` убирает только переменные родительской сессии и настроенные креды
  (`internal/execution/env.go`). `ANTHROPIC_API_KEY`, `AWS_*`, `GITHUB_TOKEN`,
  `SSH_AUTH_SOCK`, `~/.ssh` и сеть доступны коду, который написала модель. `test.sandbox`
  по умолчанию выключен. Для продукта, который продаётся безопасностью, такой дефолт
  неприемлем. Довод D7 (allowlist ломает аутентификацию) относится к CLI провайдеров, а не
  к тестам.
- **Версия CLI провайдера не проверяется.** Флаги `--restricted`, `--permission-prompts none`
  и `--tools` проверены на claude 2.1.283/2.1.287. Если после обновления CLI семантика флага
  изменится, получится то самое «тихое понижение», которое CLAUDE.md называет единственным
  недопустимым сбоем. При старте `claude --version` не сравнивается ни с чем.
- Даже в sandbox тест может записать секрет из окружения в файл репозитория. Guard следит
  только за protected paths, поэтому секрет попадёт в diff. Сейчас это не утечка (нет
  push), но станет ею с задачами W1/W2.

### 0.4 Результат не доведён до конца
- Изменения остаются в рабочем дереве: нет коммита, ветки, MR и человекочитаемого отчёта
  для ревьюера.
- Run занимает рабочую копию разработчика (`require_clean_worktree`), пока идёт прогон,
  работать в ней нельзя.

### 0.5 Порог входа
- Конфиг — около десяти секций, включая вероятностные пороги, которые пользователь не
  может осмысленно выставить. Пример конфига по умолчанию указывает на Jev, к которому у
  клиентов нет доступа.
- `MVP.md` весит 105 КБ, `README.md` — 38 КБ. Нет `init`, нет `doctor`. Sandbox есть
  только в Linux (bwrap), а большая часть разработчиков сидит на macOS.

### 0.6 Риск самого направления
- Фактически один вендор (claude CLI). Anthropic каждый месяц добавляет в Claude Code
  стадии, ревью, hooks и субагентов. Голая «цепочка стадий» станет встроенной функцией
  платформы. Защищает только то, что вендор делать не будет: управление, аудит,
  детерминированные гейты, on-prem и встраивание в процесс команды.
- Коммерческое использование поверх Claude Code требует авторизации по API-ключу (или
  Bedrock/Vertex), а не логина в подписку claude.ai. Это нужно проверить юридически (P6).
- Риск перестараться: 37 тыс. строк, из них около 5 тыс. — TUI. Опасно продолжать
  полировать инфраструктуру, не проверив ценность. Поэтому фаза 0 идёт первой.

### Вывод
Порядок: **(1) закрыть дефекты безопасности и надёжности → (2) построить бенчмарк и честно
сравнить с голым Claude Code → (3) поднять качество implement → (4) довести результат до
MR → (5) функции управления для команд**. Позиционирование — «управляемый AI-конвейер
разработки с доказуемыми гейтами для команд, которым нельзя просто дать агенту shell».

**2026-10-26, по данным бенча (B4, `bench/DECISION.md`):** адаптивный выбор стадий по
качеству не отличим от голого Claude Code и стоит дороже. Это подтверждает позиционирование
выше, поэтому следующая фаза — 3 (MR), а decision упрощается в Q8.

### [x] S1. Передавать промпт через stdin и ограничить вставляемые данные — P0 · M
**Зачем:** дефект 0.3. Сейчас большой diff или лог ломает вызов и раздувает стоимость.
**Как сделать:**
1. Проверить на текущей версии claude, что `--print` без позиционного промпта читает его

2. В `execution.Spec` добавить `Stdin io.Reader` (если его нет) и передавать промпт через

4. Сама обрезка — в `action` (`fence` не трогать), чистая функция с тестами.
**Готово, когда:** интеграционный сценарий с diff 1 МБ и логом теста 1 МБ проходит.

### [x] S2. Тестовая команда: окружение по allowlist и sandbox по умолчанию — P0 · M
**Зачем:** дефект 0.3. Код модели не должен видеть креды разработчика.

### [~] Q2. Узкий инструмент проверки внутри implement (без shell) — P0 · L
**Зачем:** проблема 0.2 — главный рычаг качества. Модель должна уметь запустить тесты
внутри своей сессии, но не получить shell.
**Идея:** оркестратор сам работает как MCP-сервер со строго фиксированными инструментами.
Модель вызывает `run_tests` без свободных аргументов, а команда берётся из конфига. Это
не shell и не настраиваемое разрешение: набор инструментов зашит в Go.
**Как сделать:**
1. Подкоманда `orchestrator mcp-verify --repo <dir> --run <id>` — stdio MCP-сервер на Go.
   Без сторонних зависимостей, если протокол реализуется компактно, иначе — проверенная
   маленькая библиотека.
2. Инструменты:
   - `run_tests` — без аргументов. Запускает `test.command` через `testexec.Runner`
     **только в sandbox** (`test.sandbox: bwrap` обязателен для включения Q2, иначе
     fail-fast) и с окружением по allowlist (S2). Возвращает код возврата и ограниченный
     (S1) вывод.
   - `run_check {name}` — `name` из закрытого списка `checks:` (Q5).
   - Опционально `run_tests {filter}` с фильтром по regex `^[A-Za-z0-9_./:-]{1,200}$`,
     передаётся **только через переменную окружения** `ORCH_TEST_FILTER`. Оператор сам
     решает, использовать ли её в `test.command`. Никакой подстановки в строку команды.
3. Guard: **перед** каждым запуском сравнить protected paths и отпечаток git с моментом
   начала implement. Код модели нельзя исполнять, если она уже тронула hooks, CI или
   конфиг: при расхождении инструмент возвращает ошибку и пишет маркер, по которому
   dispatcher проваливает шаг.
4. Лимиты: `limits.verify.max_calls_per_step` (например, 8) и общий таймаут на вызов.
5. Подключение — через существующую инфраструктуру extensions
   (`--mcp-config` + `--allowed-tools mcp__orch__run_tests`), но **встроенно**: включается
   ключом `implement.verify: true`, а не пользовательским `extensions.mcp`.
6. Итоговый шаг `test` остаётся и остаётся источником истины. Внутренний `run_tests` —
   только подсказка модели.
7. Live-проверка в `test/security`: модель в implement не может запустить что-то, кроме
   `test.command`. Инструмент не исполняется после изменения `.git/hooks`. Фильтр с `;`
   или `$(...)` отвергается.
8. Записывать каждый вызов `run_tests` в `run.json` (`executions[].verify_calls`).
**Готово, когда:** B2 показывает рост pass rate конфигурации с Q2 относительно D без

7. Режим по умолчанию — `execution.isolation: worktree`. Старое поведение —

2. Проверка **по фактическому diff** после каждого implement (diff — истина, план —
   нет). `deny_change` → нарушение как у guard'а. `require_stages`, которых нет в
   workflow → run останавливается: «добавьте стадии через --stage или разрешите в
   конфиге». Workflow на лету не перестраивается — детерминизм важнее.
3. `approval: manual` → перед коммитом (W1) нужен интерактивный gate, в CI — отказ.
4. `decision.json` и `report.md` показывают, какие правила сработали.
**Готово, когда:** сценарии deny/require/approval покрыты интеграционными тестами.

### [x] G5. Калибровка порогов по истории — P2 · M (после B3 и накопления данных)
**Зачем:** уникальная фича: «конвейер подстраивается под ваш репозиторий и остаётся
детерминированным».
**Как сделать:** `orchestrator decisions calibrate --runs <dir>` читает `decision.json`
и `outcome` (B3), для каждой стадии подбирает порог, максимизирующий успех на единицу
стоимости, и печатает **предлагаемый diff конфига** с обоснованием. Автоматически ничего
не применяет. `policy.version` пишется в `decision.json`, чтобы сравнивать прогоны до и
после.
**Откуда сигнал в обычной работе.** Run видит только исход выбранного workflow, контрфакта
нет. Источники меток:
1. *Прокси пользы из `run.json`:* review вернул fail/medium и implement исправил → review
   окупился; тесты упали после первого implement → testing окупился; на той же сложности
   без plan/analysis больше `fix_iterations`, чем с ними → они окупаются; стадия включена,
   ничего не изменила, run прошёл с первого раза → кандидат на повышение порога.
2. *Явные метки оператора (самые честные):* `--stage` добавил стадию, которую решение не
   включило → «стадия нужна» (для этого в таком run всё равно спрашивать и записывать
   вероятности); отказ от коммита в конце или повторный run той же задачи → плохой исход.
3. *Контролируемое исследование (opt-in):* если P стадии в полосе ±0.05 от порога, с малой
   вероятностью переключить стадию и записать это в `decision.json` — единственный источник
   контрфакта. Нарушает «одно решение → один workflow», поэтому только флагом и
   детерминированно (например, по хешу id run'а).
**Модели — по той же схеме** (`by_complexity`): много `fix_iterations`/провалов на уровне
сложности → поднять модель или effort; всё проходит с первой попытки → попробовать дешевле;
проверять дешёвую модель тем же opt-in на части run'ов этого уровня.
**Ограничение:** на одном репозитории данных мало — пересчитывать раз в несколько десятков
run'ов, не после каждого.
**Сейчас:** пороги стадий в example подняты вручную по первому раунду бенча (MVP.md §9.1) —
это поправка, а не калибровка: нужны задачи, на которых analysis, planning или review
меняют исход.

### [x] G6. Форма решения: размер, шаблоны, эскалация — P1 · M
**Зачем:** вероятности шести стадий повторяли одну оценку «насколько задача большая»:
simple — все стадии ниже порога, complex — все выше, `force[complex]` перекрывал остальное,
а сложность почти всегда была `medium`, так что `by_complexity` не имел смысла. На 43
решениях opus planning и review коррелируют с размером при r = 0.94 и 0.83.
**Сделано** (`specs/decision-shape/`, MVP.md §9, §9.1, §31.1, §44.8, §45.4): сложность — одно
число size = P(medium) + 2·P(complex), уровни режутся `policy.complexity.cuts` по квантилям
истории; спрашиваются только development, research и analysis, остальное даёт шаблон
уровня (`policy.stages.force`) и «testing вместе с development»; `decisions calibrate`
показывает разброс size и избыточные стадии и предлагает cuts по долям и по исходам;
`actions.implement.escalate` поднимает модель на уровень для исправления после упавшего
test или review; запись `by_complexity.<level>` может задать свою `escalate: {model, effort}`
(DS08, и для complex), а первый implement после плана начинает с его `affected_files`.
**Открыто:** size распределяет задачи по моделям, но на этих данных не предсказывает, какой
задаче понадобится исправление (≈45% на любом размере). Сравнить модели решений на одних и
тех же задачах (конфиг B бенча с `decision.model: opus`).
